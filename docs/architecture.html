Architecture guide

How Berlin Calling works

Two single-page apps, one API, six small backend services that each own their own data, and an event bus that ties them together. Everything is serverless — there is no machine to maintain, and at rest it costs almost nothing.

1 · The request path

Browsers load the static apps from CloudFront and call the API on the same domain under /api/* — CloudFront forwards those to API Gateway. Sign-in happens directly against Cognito; every API call then carries a token that one of two authorizers checks before any service code runs.

3 · The event backbone

Writes publish a small event to one EventBridge bus. That's how services cooperate without touching each other's tables: the activity service records history, and media/engagement keep tiny event-carried copies of listing state ("is it published? what's its title?") so they can make decisions locally.

4 · Client interaction tracking

The thing you asked for specifically: knowing what the client actually does on the site. Two signal paths feed the same place.

5 · Who can do what

Client

Signs in to the customer pool (self-registered or invited with a temp password). Sees only searches they're a member of, and only published listings with admin-private fields removed. Can rate, comment, and view the hours ledger. Every request's memberships come from the Lambda authorizer — handlers just compare.

Viewer

Same as client, except star ratings are blocked (they're nudged to rate in a comment instead) — mirroring the original prototype's behavior.

Admin

Separate pool: no self-signup, strong password, TOTP MFA required, must hold the admin group claim. Full control over every search. Every mutation is written to the permanent audit log with before/after snapshots.

Defense in depth for tenant isolation: (1) the authorizer only injects the caller's own search memberships, (2) handlers check the requested search against that map, (3) engagement/media verify listing↔search identity from event-carried state before accepting writes.

6 · Data design in one paragraph

Every table uses the same generic key pair (PK/SK) with entity-prefixed values, so one table per service holds several record types. A search is the tenancy unit: almost everything lives in a SEARCH#<id> partition, which makes "load the whole board" one query. IDs are ULIDs — lexicographically time-ordered, so "newest first" is free.

7 · Life of a request: Brian rates a listing ★★★★★

  1. Brian clicks 5 stars → PUT /api/v1/searches/S1/listings/L7/rating with his customer-pool token.
  2. CloudFront (www) forwards /api/* to API Gateway, same origin.
  3. The Lambda authorizer verifies the token signature against the customer pool and queries the search table's membership index: Brian → {S1: client}. Cached 5 min.
  4. The engagement handler validates the body with zod, checks Brian's role in S1 (clients may rate; viewers may not), and checks its local listing meta: L7 belongs to S1 and is published.
  5. The rating is upserted (one per user per listing) and rating.saved — "Brian rated ‘Top-floor flat with roof terrace’ 5★" — goes onto the bus.
  6. The activity sink writes it to S1's feed. Next time JJ opens the dashboard, it's right there; the engagement tab's counters already reflect Brian's earlier card-expands and photo views from the tracking beacon.

Meanwhile JJ's own actions (publishing a listing, marking hours paid) follow the same path through the admin authorizer — and additionally land in the permanent audit log.
