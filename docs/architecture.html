Architecture guide

How Genau Here works

Two single-page apps, one API, six small backend services that each own their own data, and an event bus that ties them together. Everything is serverless — there is no machine to maintain, and at rest it costs almost nothing. In production the client site is genauhere.de (and www), the admin console admin.genauhere.de; dev lives on CloudFront URLs.

Reading order for newcomers: the request path (1), then the service catalog (2) and the event backbone (3) — that is 80% of the system. The import pipeline (4) is the one piece with moving parts of its own. Come back for data design and the worked example when you start changing code.

1 · The request path

Browsers load the static apps from CloudFront and call the API on the same domain under /api/* — CloudFront forwards those to API Gateway, so there is no CORS dance in production. Sign-in happens directly against Cognito; every API call then carries a token that one of two authorizers checks before any service code runs. The custom domains are plain Route53 alias records pointing at the two distributions, with certificates issued by ACM; the apps don't know or care which hostname they are served from.

3 · The event backbone

Writes publish a small event to one EventBridge bus. That's how services cooperate without touching each other's tables: the activity service records history, media/engagement keep tiny event-carried copies of listing state ("is it published? what's its title?") so they can make decisions locally, listings keeps a copy of each search's brief and settings so it can compute what a search may see, and the bus is also how a link import is handed to its worker.

4 · The listing import pipeline

JJ pastes a portal link (ImmobilienScout24, Kleinanzeigen, …) into the admin app's Link inbox and clicks Import. Fetching a page through a rendering proxy and asking the AI model can take over a minute, longer than API Gateway allows a request to last, so the work runs as a background job and the browser watches it.

  1. Queue. POST /api/v1/admin/import stores a job row (queued) and publishes listing.import.requested; it answers 202 immediately.
  2. Fetch. The import worker Lambda (five-minute budget) picks the event up. It fetches the page directly, or straight through the ScrapingBee proxy for portals known to block cloud IPs; the proxy renders JavaScript through German residential addresses.
  3. Parse. JSON-LD, meta tags and the German key/value table (Kaufpreis, Wohnfläche, Zimmer, Etage, Baujahr, Hausgeld, Provision…) are read with plain code — no AI needed for the numbers.
  4. Extract. The page text goes to Claude with a fixed output schema. It fills what the parser missed (district from a postcode, floor from prose) and writes every text field in English, translating the German page. If the key isn't configured or the call fails, the import still succeeds with "page markup only".
  5. Save. A hidden draft listing is created, the inbox link is marked done, and the job row gets the result. Progress (fetching → extracting → saving) is written to the job as it goes.
  6. Watch. The admin app polls GET /api/v1/admin/import/{jobId} every 1.5 s and shows a house being built, one stage per step. When the job is done it imports the photos found on the page in batches of six (the media service downloads them into S3) and opens the editor with every auto-filled field marked for review.
Pasted text (the fallback when a portal blocks even the proxy) skips the queue: it only needs the AI call, so the API reads it inline. A job that overruns is marked failed with a timeout error rather than dying silently, and can simply be retried. Job rows expire after a day. The AI and proxy keys live in Secrets Manager and are read at runtime — storing a key takes effect within a minute, no redeploy.

6 · Who can do what

Client

Signs in to the customer pool (self-registered or invited with a temp password). Sees only searches they're a member of, and only published listings with admin-private fields removed. Can rate, comment, and view the hours ledger. Every request's memberships come from the Lambda authorizer — handlers just compare.

Viewer

Read-only: same visibility as a client, but ratings and comments are rejected by the engagement handler. Viewers also can't invite others.

Admin

Separate pool: no self-signup, strong password, TOTP MFA required, must hold the admin group claim. Full control over every search. Every mutation is written to the permanent audit log with before/after snapshots.

Defense in depth for tenant isolation: (1) the authorizer only injects the caller's own search memberships, (2) handlers check the requested search against that map, (3) engagement/media verify listing↔search identity from event-carried state before accepting writes.

Invitations, in practice

Inviting an email address from either app does one of three things, and the app says which: a new account is created and Cognito emails a temporary password; an address that was invited before but never signed in gets the invitation again with a fresh temporary password (they expire after 7 days); an address with a working account is simply given access, with no email. Two consequences worth knowing: "forgot password" cannot reset an account that is still on its temporary password — Cognito quietly reports success and sends nothing, because the customer app hides whether an account exists — so re-invite instead; and invitation/reset emails come from Cognito's built-in mailer (50 a day, spam-prone) until an SES sender is configured.

7 · Data design in one paragraph

Every table uses the same generic key pair (PK/SK) with entity-prefixed values, so one table per service holds several record types. A search is the tenancy unit: almost everything lives in a SEARCH#<id> partition, which makes "load the whole board" one query. The exception is listings, which form one global pool: a search sees a published listing when it matches the search's brief and settings (a copy of which the listing service keeps, fed by events), or when JJ shared it by hand, and never when she hid it — computed on read, never copied per search. IDs are ULIDs — lexicographically time-ordered, so "newest first" is free.

8 · Life of a request: Brian rates a listing ★★★★★

  1. Brian clicks 5 stars → PUT /api/v1/searches/S1/listings/L7/rating with his customer-pool token.
  2. CloudFront (genauhere.de) forwards /api/* to API Gateway, same origin.
  3. The Lambda authorizer verifies the token signature against the customer pool and queries the search table's membership index: Brian → {S1: client}. Cached 5 min.
  4. The engagement handler validates the body with zod, checks Brian's role in S1 (clients may rate and comment; viewers are read-only), and checks its local listing meta: L7 belongs to S1 and is published.
  5. The rating is upserted (one per user per listing) and rating.saved — "Brian rated ‘Top-floor flat with roof terrace’ 5★" — goes onto the bus.
  6. The activity sink writes it to S1's feed. Next time JJ opens the dashboard, it's right there; the engagement tab's counters already reflect Brian's earlier card-expands and photo views from the tracking beacon.

Meanwhile JJ's own actions (publishing a listing, marking hours paid) follow the same path through the admin authorizer — and additionally land in the permanent audit log.

10 · Environments, domains and secrets

There are two complete copies of everything: dev (stacks JJ-dev-*, CloudFront URLs, WAF off, data deleted on teardown) and prod (JJ-prod-*, the custom domains, WAF on, data retained). Both come from the same code; the only differences are the knobs in infra/cdk.json under environments.dev and environments.prod.

KnobWhat it controls
domainHostnames for the two sites (customer, customerAliases such as www, admin) in a Route53 zone (zoneName). Set only in prod. Needs the zone to exist and the registrar to delegate to it before deploying; the deploy then issues certificates, attaches the names to CloudFront and writes the DNS records.
notifyURLs used in emails (Cognito invitations/resets, activity notifications) and the SES sender + JJ's inbox for notifications. Without mailFrom, no activity emails are sent; Cognito's own mailer still handles invitations.
listingImportThe scraping-proxy URL template (with {url} and {key}) and, optionally, the AI model id.
enableWaf, removalPolicy, logRetentionDaysThe usual dev/prod differences: protection, data retention, log retention.

Anything secret — the Anthropic key for AI extraction, the ScrapingBee key for the proxy — is not in cdk.json. The Listing stack creates a Secrets Manager secret per key with a placeholder value (jj/<env>/listing-import/ai-api-key, …/proxy-api-key); you store the real value with aws secretsmanager put-secret-value, and the Lambdas read it at runtime, re-checking a missing key every minute. The deploy pipeline is GitHub Actions: every merge to main deploys dev automatically and then waits for a human to approve the production step.
