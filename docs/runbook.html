Runbook · AWS account → running dev environment

Deploy Genau Here

Everything from a brand-new AWS account to a working dev deployment of the apartment-search platform, the CI/CD hookup for the justinmccoy/realtor repo, and then production on your own domain with AI import enabled. 1

Create the AWS account

~10 min

Skip to step 2 if you already have an account you want to use.

  1. Go to aws.amazon.com/free → Create an AWS account.
  2. Use an email you control long-term (an alias like you+aws@… works). This becomes the root user.
  3. Account name: anything (jj-realtor is fine). Pick Personal.
  4. Add a credit card (required even on the free tier), verify your phone, choose the Basic (free) support plan.
New accounts can take a few minutes to fully activate. If a later step says the account isn't ready, wait 10 minutes and retry.
2

Secure the root user

~5 min

The root user can do (and spend) anything. You'll use it exactly twice — here, and never again for daily work.

  1. Sign in to the AWS Console as root.
  2. Top-right account menu → Security credentials.
  3. Under Multi-factor authentication → Assign MFA device → Authenticator app → scan the QR with the same authenticator you'll use for the admin site.
  4. Confirm there are no root access keys (section "Access keys" should be empty — never create one).
  5. Note your 12-digit Account ID from the same menu — you'll need it everywhere below as <ACCOUNT_ID>.
3

Create your admin identity (IAM Identity Center)

~10 min

Daily work happens as an SSO user with short-lived credentials — no long-lived access keys on your laptop.

  1. Console search → IAM Identity Center → Enable (accept the default "organization instance"; region prompt: pick Europe (Frankfurt) eu-central-1).
  2. Note the AWS access portal URL shown on the dashboard (like https://d-xxxxxxxxxx.awsapps.com/start) — call it <SSO_START_URL>.
  3. Users → Add user: username justin, your email, name. Accept the email invite and set a password + MFA.
  4. Permission sets → Create permission set → Predefined → AdministratorAccess → create.
  5. AWS accounts → tick your account → Assign users or groups → pick justin → pick AdministratorAccess → submit.
Shortcut if you'd rather not set up Identity Center (less secure)

Create a classic IAM user instead: Console → IAM → Users → Create user justin-cli → attach AdministratorAccess → create an access key ("CLI use") → run aws configure with the key, secret, and region eu-central-1. Works with every command below (drop the --profile jj parts). Long-lived keys on disk are the trade-off.

4

Set a budget alarm

~3 min

This stack costs ~$2–3/mo for dev (and ~$15–18 for prod later). An alarm catches surprises — a misconfigured loop, a forgotten NAT gateway, anything.

  1. Console → Billing and Cost Management → Budgets → Create budget.
  2. Template: Monthly cost budget, amount $25, your email as recipient. Done.
5

Install & configure the AWS CLI

~5 min
brew install awscli
aws --version        # want: aws-cli/2.x

Configure an SSO profile named jj (answers shown after each prompt):

aws configure sso
# SSO session name:      jj
# SSO start URL:         <SSO_START_URL>
# SSO region:            eu-central-1
# SSO registration scopes: (press Enter for default)
# → browser opens: sign in as justin, Allow
# Pick your account + AdministratorAccess
# Default client region: eu-central-1
# Output format:         json
# Profile name:          jj

Make it the default for this shell and verify:

export AWS_PROFILE=jj          # add to ~/.zshrc to make it stick
aws sts get-caller-identity    # shows your <ACCOUNT_ID>
SSO sessions expire (usually 8–12 h). When any aws/cdk command says credentials are expired: aws sso login and re-run.
6

Bootstrap CDK (once per account)

~5 min

Bootstrapping creates the S3 bucket and IAM roles CDK deploys through. Two regions: eu-central-1 for everything, and us-east-1 because CloudFront requires its WAF + certificates to live there.

cd ~/JDevelops/JJ-ApartmentSearchTool
export AWS_PROFILE=jj
pnpm install
pnpm --filter @jj/infra exec cdk bootstrap aws://<ACCOUNT_ID>/eu-central-1
pnpm --filter @jj/infra exec cdk bootstrap aws://<ACCOUNT_ID>/us-east-1
Success looks like: ✅ Environment aws://…/eu-central-1 bootstrapped.
7

Deploy the dev environment

~15 min
pnpm deploy:dev

That deploys all 12 stacks (JJ-dev-Platform, -Auth, -SearchData, -Edge, -Api, -Frontend, and the six services). First run takes ~10–15 min — CloudFront distributions are the slow part. Then publish the two web apps:

./scripts/deploy-frontends.sh dev

The script ends by printing your two URLs:

  customer: https://dXXXXXXXXXXXX.cloudfront.net
  admin:    https://dYYYYYYYYYYYY.cloudfront.net

Save them — referenced below as <CUSTOMER_URL> and <ADMIN_URL>.

8

Create the first admin (you)

~5 min

Admins can't self-register — create the account and put it in the admin group:

POOL_ID=$(aws cloudformation describe-stacks --stack-name JJ-dev-Auth \
  --query "Stacks[0].Outputs[?OutputKey=='AdminPoolId'].OutputValue" --output text)

aws cognito-idp admin-create-user --user-pool-id "$POOL_ID" \
  --username <YOUR_EMAIL> \
  --user-attributes Name=email,Value=<YOUR_EMAIL> \
      Name=email_verified,Value=true Name=name,Value="JJ"

aws cognito-idp admin-add-user-to-group --user-pool-id "$POOL_ID" \
  --username <YOUR_EMAIL> --group-name admin

Cognito emails you a temporary password (it sits alone on its own line in the email — copy exactly that; it is valid for 7 days). Now open <ADMIN_URL> and sign in:

  1. Email + the temporary password from the email.
  2. Set your real password (14+ chars, upper/lower/digit/symbol).
  3. Enrol MFA: the page shows a TOTP secret — add it to your authenticator app, enter the 6-digit code.
Without the admin-add-user-to-group call, sign-in works but every API call returns 403 — the group claim is what authorizes admin routes.
9

Seed data & verify end-to-end

~10 min

Load the example Berlin content (8 listings, brief, hours):

export SEED_API_BASE=<CUSTOMER_URL>
export SEED_ADMIN_POOL_ID=$POOL_ID
export SEED_ADMIN_CLIENT_ID=$(aws cloudformation describe-stacks --stack-name JJ-dev-Auth \
  --query "Stacks[0].Outputs[?OutputKey=='AdminClientId'].OutputValue" --output text)

npx tsx scripts/seed.ts --env dev
# prompts: admin email, password, TOTP code

Verification checklist:

  • Admin app (<ADMIN_URL>): the "Brian" search appears; Listings shows 8 rows; publish toggles work; upload a photo on one listing.
  • Invite a client: Search → Members → invite an email you control (role client). The toast tells you what happened: a new account with an emailed temporary password, a re-sent invitation for an address that never signed in, or plain access for an existing account (no email).
  • Customer app (<CUSTOMER_URL>): sign in with the emailed temp password → set your own → the board renders with the artifact design; rate a listing; post a comment.
  • Link import: Listings → Link inbox → paste a portal URL → Import. Watch the house get built; the draft opens in the editor. Without the AI key the text stays German and the warning says so; without the proxy, ImmobilienScout24/Kleinanzeigen report "blocked" and offer the paste fallback. Both keys are stored in step 11.
  • Tracking loop: back in the admin app → Engagement — your clicks from the customer app show up (expands, photo views), and Dashboard shows "last client activity".
10

Wire up CI/CD (GitHub → AWS)

~10 min

Lets the Deploy workflow in justinmccoy/realtor deploy on push — no AWS keys stored in GitHub, just an OIDC trust.

10a — OIDC provider (once per account):

aws iam create-open-id-connect-provider \
  --url https://token.actions.githubusercontent.com \
  --client-id-list sts.amazonaws.com

10b — the deploy role. The two JSON files below don't exist yet — you create them as one-time inputs for the aws iam commands. Save them anywhere temporary (e.g. cd "$(mktemp -d)" first — not in the project repo); run the commands from that same directory so the file:// paths resolve; delete the files afterwards. Tip: set ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text) and use ${ACCOUNT_ID} in heredocs to avoid hand-editing. First, trust.json:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::<ACCOUNT_ID>:oidc-provider/token.actions.githubusercontent.com"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" },
      "StringLike":  { "token.actions.githubusercontent.com:sub": [
        "repo:justinmccoy/realtor:*",
        "repo:justinmccoy@*/realtor@*:*"
      ]}
    }
  }]
}
GitHub may issue ID-pinned subject claims of the form repo:owner@<ownerId>/repo@<repoId>:… — the second pattern covers that. For tighter security, replace the * after the @s with your actual numeric IDs (shown in any workflow's OIDC token, or via gh api repos/justinmccoy/realtor --jq '.id, .owner.id').

Save as deploy-policy.json (CDK does the heavy lifting through its own bootstrap roles; this role only assumes them, reads stack outputs, and publishes the frontends):

{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "AssumeCdkRoles", "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::<ACCOUNT_ID>:role/cdk-*" },
    { "Sid": "ReadStackOutputs", "Effect": "Allow",
      "Action": "cloudformation:DescribeStacks", "Resource": "*" },
    { "Sid": "PublishFrontends", "Effect": "Allow",
      "Action": ["s3:ListBucket","s3:GetObject","s3:PutObject","s3:DeleteObject"],
      "Resource": [
        "arn:aws:s3:::jj-customer-web-*", "arn:aws:s3:::jj-customer-web-*/*",
        "arn:aws:s3:::jj-admin-web-*",    "arn:aws:s3:::jj-admin-web-*/*" ] },
    { "Sid": "InvalidateCache", "Effect": "Allow",
      "Action": "cloudfront:CreateInvalidation", "Resource": "*" }
  ]
}
aws iam create-role --role-name gh-deploy-realtor \
  --assume-role-policy-document file://trust.json
aws iam put-role-policy --role-name gh-deploy-realtor \
  --policy-name deploy --policy-document file://deploy-policy.json
aws iam get-role --role-name gh-deploy-realtor \
  --query Role.Arn --output text     # ← copy this ARN

10c — GitHub side (or via the web UI under Settings):

gh secret set AWS_DEPLOY_ROLE_ARN --repo justinmccoy/realtor \
  --body "arn:aws:iam::<ACCOUNT_ID>:role/gh-deploy-realtor"
gh api -X PUT repos/justinmccoy/realtor/environments/dev
gh api -X PUT repos/justinmccoy/realtor/environments/production

Then in the browser: repo → Settings → Environments → production → Required reviewers → add yourself. That checkbox is the manual approval gate before prod deploys.

Test it: push any commit to main (or Actions → Deploy → Run workflow). Expect: verify ✓ → deploy-dev ✓ → deploy-prod ⏸ waiting for your approval.

Approving deploy-prod the first time creates the whole prod environment (~$15–18/mo, WAF included). Leave it unapproved until you actually want prod.
11

Go to production

~45 min + DNS wait

Prod is the same stacks under JJ-prod-*. It comes into existence the first time you approve the production step of a Deploy run (Actions → the run → Review deployments → production → Approve). Then, in this order:

11a — Custom domains. Create a public hosted zone and delegate your domain to it at the registrar:

aws route53 create-hosted-zone --name genauhere.de \
  --caller-reference "genauhere-$(date +%s)"
aws route53 get-hosted-zone --id <ZONE_ID> --query DelegationSet.NameServers
# → enter those four nameservers at the registrar (Squarespace Domains: DNS → custom nameservers)
dig +short NS genauhere.de     # wait until this shows the awsdns names
Moving the nameservers moves all DNS for the domain. Recreate any records you need (mail MX, etc.) in the zone first. And don't put the domain block below into cdk.json before the zone exists: the Edge stack looks the zone up at synth time, and a missing zone blocks the whole prod deploy.

Once delegation is live, set the prod block in infra/cdk.json → environments.prod:

"domain": {
  "zoneName": "genauhere.de",
  "customer": "genauhere.de",
  "customerAliases": ["www.genauhere.de"],
  "admin": "admin.genauhere.de"
},
"notify": {
  "customerUrl": "https://genauhere.de",
  "adminUrl": "https://admin.genauhere.de",
  ...
}

Merge, approve the production deploy, and allow 20–30 minutes: ACM validates the certificates through the zone, CloudFront picks up the names, the A records are written, CORS and Cognito's email links switch to the new hostnames. Verify from a terminal (your own machine may cache old DNS for hours — a phone on mobile data is the quickest second opinion):

dig +short genauhere.de @1.1.1.1          # CloudFront addresses
curl -sI https://www.genauhere.de/ | head -1   # HTTP/2 200
curl -sI https://admin.genauhere.de/ | head -1

11b — First admin on the prod pool. Same as step 8 with --stack-name JJ-prod-Auth.

11c — AI extraction and the fetch proxy. Get an Anthropic key from the Claude Console (Settings → API Keys → Create Key; billing must be set up) and a ScrapingBee key from its dashboard. Store both in the secrets the Listing stack created — the raw key only, no quotes or JSON:

aws secretsmanager put-secret-value \
  --secret-id jj/prod/listing-import/ai-api-key --secret-string "sk-ant-…"
aws secretsmanager put-secret-value \
  --secret-id jj/prod/listing-import/proxy-api-key --secret-string "<SCRAPINGBEE_KEY>"

They take effect within a minute, no redeploy. The proxy URL template is already set for prod in cdk.json (ScrapingBee with JS rendering and German proxies). Test with one link import from the admin app: the draft should read in English and the import summary should say the page came via proxy.

11d — Email at volume (optional, later). Cognito's built-in mailer sends the invitations and password resets from no-reply@verificationemail.com, capped at 50 a day and often filed as spam. When there are more than a handful of clients, verify a sender address in SES, set notify.mailFrom (and notify.adminEmail for JJ's activity notifications) in cdk.json, and redeploy.

Done when all three hostnames serve the apps over HTTPS, you can sign in to admin.genauhere.de with MFA, an invited client receives their email, and a link import comes back in English.

Troubleshooting

SymptomFix
Unable to locate credentials / token has expiredaws sso login, and check echo $AWS_PROFILE says jj.
cdk bootstrap: AccessDeniedYou're not on the Administrator permission set — re-check step 3.5, then aws sso login.
deploy: …is not bootstrapped mentioning us-east-1Run the second bootstrap command from step 6 — the Edge stack lives in us-east-1.
Frontend loads but shows "Missing configuration"You opened a local dev build without .env.local. The deployed CloudFront URLs are configured by deploy-frontends.sh; re-run it after infra changes.
Admin sign-in OK but every page errors 403User isn't in the admin group — step 8's second command.
Invite email never arrivesCheck spam first. Re-invite the same address from the admin app: if they never signed in, a fresh temporary password is emailed; if the toast says "already have an account", the person can sign in with their existing password. Cognito's default mailer stops at 50 emails a day — move to SES (step 11d) before that matters.
"Forgot password" says a code was sent, nothing arrivesMost likely the address was invited but never signed in: Cognito can't reset an account still on its temporary password and, with user-existence errors hidden, reports success anyway. Re-invite them instead. Otherwise check the spelling of the address and the spam folder.
Link import says "AI extraction is not configured" after storing the keyThe secret value must start with sk-ant- and be the bare key. Wait a minute (the Lambda re-checks missing keys every 60 s) and try again.
Import reports "blocked" for ImmobilienScout24 / KleinanzeigenThe proxy isn't active: the message says if the proxy key is missing (step 11c), or the proxyUrlTemplate for that environment is empty in cdk.json. Until then use "Paste the page text instead".
Import stays on "Clearing the plot" and times outThe worker never picked up the job: check the listing-import-worker Lambda's logs and the EventBridge rule in the Listing stack. The draft is not created in that case; retry.
Prod deploy fails at "Found zones: [] for dns:…"The domain block was deployed before the Route53 zone existed or before delegation. Create the zone (step 11a) — or temporarily set "domain": null — and rerun.
GitHub Actions runs sit "queued" for minutes with no runnerUsually a GitHub incident — check githubstatus.com. Nothing in the repo blocks them; gh run rerun <id> if one is still stuck afterwards.
Several Deploy runs waiting for production approvalApprove only the newest; it contains the earlier merges, and the prod jobs share a concurrency group so they would otherwise run one after another.
GitHub deploy job: Not authorized to perform sts:AssumeRoleWithWebIdentityTrust policy sub must match repo:justinmccoy/realtor:* exactly; OIDC provider from 10a must exist.
Nuke everything (dev)pnpm --filter @jj/infra exec cdk destroy -c env=dev --all
